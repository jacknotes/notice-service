# Web 后端工程（web-backend-engineer）

以**专业后端工程师**的标准工作：写功能时把**分层、安全、性能、质量**一次性做对；修 BUG 时**定位根因、最小改动、绝不带出回归**。本 SKILL 是「怎么想、怎么干」的方法论与纪律，配套技术栈默认 **Go + Gin + MySQL（database/sql，无 ORM）**，与仓库内 `go-vue-fullstack-scaffold`（工程骨架）、`web-backend-service-testing`（黑盒测试）、`notice-service-deploy`（部署）协同使用。

> 核心理念：**先理解再动手；修的是因不是果；每一次改动都要能被验证**。任何「让症状消失」但不解决根因的补丁、任何「改一处坏三处」的修复，都是不合格的。

---

## 1. 何时使用

- 用户说「写一个接口 / 实现一个功能 / 加一个模块 / 后端怎么做」。
- 用户说「这个 BUG 帮我修一下 / 排查一下 / 定位一下 / 线上报错了」。
- 需要做后端代码审查、安全加固、性能优化、重构某段后端逻辑。

不适用：前端实现（`vue3-signal-relay-frontend`）、新项目骨架搭建（`go-vue-fullstack-scaffold`）、只对运行中的服务做黑盒测试（`web-backend-service-testing`）。

> 若任务属于**跨层 / 前后端联动**、或**分不清是前端还是后端的 BUG**，先走 `web-fullstack-engineer` 总入口定位层次，再决定落点。

## 2. 六条铁律（每次动手前默念）

1. **分层不可越界**：`handler` 只做解析→调 service→响应；`repository` 只碰 DB；业务判断只许在 `service`。任何一层越界（handler 里写 SQL、service 里直接 `http`）都是质量债。
2. **先读代码，再写代码**：动任何文件前先 `read` 完整相关调用链，确认现状、契约、既有约定，不凭记忆/猜测改。
3. **错误不吞、细节不泄**：`err` 必须被处理或显式返回；对外响应只出业务码，**绝不透出** SQL/堆栈/驱动细节。
4. **写操作先想安全与一致**：谁有权限？并发下会不会脏？失败半途会不会留半截数据？入参是否可被注入？
5. **修 BUG 先复现、找根因**：能稳定复现才谈得上「已修复」；修的是根因，不是把症状包起来。
6. **每改必验、每改防回归**：改动必须有测试/验证证据；并主动排查「同样的错是不是在别处还有」。

## 3. 分层架构与职责边界（写功能的地基）

目录与骨架沿用 `go-vue-fullstack-scaffold` §3，这里只强调**每一层的红线和合格标准**：

| 层 | 只做什么 | 红线（禁止） | 合格标准 |
|----|----------|--------------|----------|
| `handler` | 解析/校验 HTTP 参数 → 调 `service` → 统一 JSON 响应 | 写业务判断、拼 SQL、直接访问 DB | 每个 handler 短小、无 if 分支逻辑 |
| `service` | 编排业务、事务边界、权限/规则校验 | 直接操作 `*sql.DB` 拼字符串 SQL、读 HTTP 上下文 | 方法名表达业务意图，可单测 |
| `repository` | 数据存取，一个实体一个 `*_repo.go` | 做业务判断、返回领域外的东西 | 只依赖 DB 接口，参数化查询 |
| `model` | 领域模型/表结构 struct + 校验 tag | 塞 HTTP/序列化逻辑 | 与表结构一一对应 |

**约定优于纠结**：
- 错误统一转业务码（如 `code: 40001, msg: "渠道不存在"`），中间件/响应封装统一处理，handler 不手写 `c.JSON` 兜底。
- 一个实体 = model + repository + service + handler 四段式，缺一段要说明理由（纯查询可省 service？不，查询的业务规则也在 service）。
- 新增「分类/枚举/共享词表」只在一处托管，别的地方只引用（见 scaffold §9）。

## 4. 写后端功能的标准流程

```
明确需求与边界 → 设计（接口/数据/异常路径）→ 写测试或验证方案 → 实现 → 自测 + 回归
```

1. **明确边界**：输入什么、输出什么、失败有哪些情况、谁有权限、要不要幂等/并发安全。没想清楚就问用户，**不要闷头写**。
2. **先定契约再写代码**：
   - URL / method / 请求体 / 响应体 / 错误码 / 分页参数（`page/page_size/sort_by/sort_order`）。
   - 与既有接口风格保持一致（列表接口参数、时间格式、空值语义）。
3. **异常路径优先想**：参数非法、资源不存在、无权限、重复提交、并发冲突、DB 挂了——每一条都要有明确返回，而不是 panic 或 500。
4. **实现时按层推进**：model → repository（参数化 SQL）→ service（业务+事务）→ handler（解析+调用）→ router（挂路由+中间件）。
5. **自测**：至少跑通「正常 + 至少 3 种异常」；写操作测「重复提交幂等」与「并发」。
6. **回归**：改完跑 `make test` / `go vet`，确认没破坏既有用例（见 §10 回归防线）。

## 5. API 设计规范

- **REST 语义**：`GET` 读、`POST` 创建、`PUT` 全量更新、`PATCH` 局部、`DELETE` 删除；动作类用子路径（`/tasks/:id/send`）。
- **状态码**：200 成功；201 创建；204 无内容；400 参数错；401 未认证；403 无权限；404 不存在；409 冲突（重复/状态不符）；413 过大；422 校验失败；429 限流；500 服务器错（业务错一律转业务码+4xx，不滥用 500）。
- **错误响应统一**：`{code, msg, data?}`；`code` 稳定可程序判断，`msg` 给人看且不泄密。
- **分页**：`page`（从 1）、`page_size`（设上限，如 ≤100）；响应带 `total`；**排序必带稳定字段**（`sort_by` + 追加 `id` 兜底），否则翻页会重复/丢数据。
- **幂等**：创建类接口设计防重（唯一键 + `INSERT ... ON DUPLICATE` 或先查后插带唯一约束）；对账/发送类动作要有幂等键或去重键。
- **不要**在 URL 里暴露敏感参数（api_key 走 header/路径脱敏），不要用动词命名资源（`/getUser` ❌ `/users/:id` ✅）。

## 6. 数据一致性与并发（最容易出隐性 BUG 的地方）

- **事务边界**：多步写操作包在 `sql.Tx` 里，`defer tx.Rollback()` 兜底，显式 `Commit`；**查询用于决策的读与后续写**若强一致要放同一事务或加锁。
- **参数化 SQL**：一律 `?` 占位 + 参数绑定，**绝不字符串拼接用户输入**。
- **并发更新**：
  - 计数/状态流转用「条件更新」而非「先读后写」：`UPDATE ... SET status='running' WHERE id=? AND status='pending'`，用 `RowsAffected` 判是否抢到（原子认领/租约锁即此模式，见 scaffold §7）。
  - 需要「读-改-写」一致时用 `SELECT ... FOR UPDATE`（在事务内）或乐观锁（`version` 字段 + `WHERE version=?`）。
- **唯一约束兜底**：逻辑上唯一的字段（用户名/名称/编码）必须建唯一索引，靠应用层「先查后插」并发下必漏。
- **死锁**：多表更新保持固定顺序；事务尽量短；遇到死锁（`1213`）可有限重试，但**重试前想清楚事务是否可安全重放**。
- **软删除/级联**：删除保持完整性（级联删除 / 软删 `deleted_at` / 引用重置 default），不破坏外键语义。

## 7. 安全清单（写代码时的默认项）

> 完整安全项见 `go-vue-fullstack-scaffold` §6 与 `web-backend-service-testing` §6。这里只列「写每一行代码都要默认遵守」的项：

- **鉴权**：JWT 只收 HS256、算法白名单；密码/令牌比较用常数时间；敏感操作二次校验（2FA、原密码）。
- **越权**：**每个**按 ID 访问资源的 handler 都要校验「该资源是否属于当前用户 / 当前用户是否有权限」，不默认「能登进来就能看」。
- **注入**：SQL 参数化；命令执行/文件路径不拼用户输入；导出 CSV 防公式注入（`+ - = @` 转义）。
- **输出编码**：渲染第三方内容（Markdown/HTML）经 DOMPurify；JSON 输出不手拼字符串。
- **脱敏**：列表/详情不返回密钥明文；错误响应统一业务码；日志里 webhook key/token 打码；指标 label 用路由模板（`c.FullPath()`）防 api_key 泄漏与基数爆炸。
- **限制**：请求体 `http.MaxBytesReader` 上限；登录限流按「用户名+IP」复合桶；慢请求不拖垮服务（服务端显式超时）。
- **头**：安全响应头（`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`CSP`）；可信代理白名单 `TRUSTED_PROXIES`，非可信代理的转发头一律忽略。

## 8. 性能清单（写查询与接口时）

- **索引**：高频筛选/排序/关联字段有索引；`WHERE a=? AND b=?` 用联合索引；**EXPLAIN 看是否走索引**、有没有全表扫描/临时表。
- **N+1**：列表接口禁止循环查详情——用 `IN (...)` 批量取或 JOIN；关联数据一次性拉齐再内存组装。
- **查询字段**：不 `SELECT *`（尤其列表），只取需要的列；大字段（content/blob）与列表分离。
- **连接池**：`SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime` 合理配置；用完 `rows.Close()`（`defer`），否则连接泄漏。
- **分页**：大数据量用「键集分页」或至少 `LIMIT/OFFSET` + 索引；`COUNT(*)` 与列表分开，避免深分页卡顿。
- **缓存**：热点只读数据可缓存，但**必须想清楚失效**（改数据时同步失效/更新），否则缓存陈旧是新的 BUG 源；不要为了「优化」引入未经验证的缓存。
- **并发**：能用无状态/共享只读就避免锁；必要锁时锁粒度最小、时间最短。
- **过早优化是错的**：先保证正确，用指标/压测定位真热点（配合 `web-backend-service-testing` §7），**不凭感觉加缓存、加协程**。

## 9. 错误处理与可观测性

- **不吞错**：`err` 必须被返回、记录或明确忽略（`_ =` + 注释理由）；尤其 `defer` 里的 `rows.Close()`/`tx.Rollback()` 不要静默丢弃错误。
- **错误包装**：用 `fmt.Errorf("xxx: %w", err)` 保留上下文与因果链，方便定位；对外层由 handler 统一脱敏成业务码。
- **日志**：启动/关键动作/错误/慢查询打结构化日志，含 request id、用户、路由；**日志内容脱敏**，不记明文密钥/token。
- **指标**：接口 QPS/延迟/错误率/队列深度/DB 连接数暴露为 Prometheus（可选）；label 用路由模板防基数爆炸。
- **不要 panic 兜底裸奔**：加 recover 中间件转 500 并记堆栈，但**不能靠 recover 掩盖逻辑错误**（它是兜底不是解法）。

## 10. BUG 修复方法论（核心章节：从根本解决、不带出问题）

> 这是本 SKILL 的**重中之重**。用户反复强调「从根本解决、不带来任何问题」，落地为下面十步。**任何 BUG 不经过「复现 + 根因 + 回归」三步就不算修完。**

### 10.1 十步法

1. **复现（Reproduce）**：拿到触发条件（请求/入参/操作路径/日志/当时的 DB 状态）。复现不了就问用户要日志与数据，**不靠猜**。黑盒复现可复用 `web-backend-service-testing` 工具链。
2. **读链路（Read）**：沿出错路径把 handler→service→repository 完整读一遍，含中间件、事务、错误包装。**先看代码再下结论**。
3. **定位根因（Root Cause）**：用「5 why」追问到根，并区分三层——
   - **症状**（symptom）：用户看到的报错/现象。
   - **直接原因**（proximate cause）：哪里返回了错/写了坏数据。
   - **根因**（root cause）：为什么会那样——错误的假设、竞态、越界、数据不变量被破坏、遗漏的边界。
   例：症状=列表偶发 500；直接原因=某行 `rows.Scan` 报 nil；根因=某字段可为 NULL 但 model 用非指针类型接收（而非「加个 try」）。
4. **判明错误类别**（对应修法不同）：
   - 竞态/并发 → 加锁或原子操作，不是加 sleep。
   - 边界/空值/越界 → 修判定条件与类型，不是加 `if err != nil { continue }` 跳过。
   - 事务范围错/半提交 → 收进同一事务，不是事后补数据。
   - 注入/越权 → 参数化/加校验，不是前端隐藏。
   - 缓存陈旧 → 修失效策略，不是手动清缓存。
5. **评估爆炸半径（Blast Radius）**：`grep` 谁还调用了这个函数/这种模式；这个数据不变量还被谁依赖；**同样的错误在别处是否也存在**。修一处前先知道影响面。
6. **最小修复（Minimal Fix）**：只改必要的行，直击根因；**不顺手重构无关代码**（重构另开一次提交）。禁止症状补丁：`recover` 吞错、`time.Sleep` 等竞态、`WHERE 1=1` 屏蔽、对错误值特殊 case。
7. **数据修复（若已污染）**：BUG 若已写入坏数据，评估是否需要一次性回填/修复 SQL，且**幂等、可回滚、先备份**。
8. **回归测试（Regression Test）**：写一个**修之前必挂、修之后必过**的测试，锁定根因（并发用并发测试、边界用边界用例）。
9. **验证无回归（Verify）**：`make test`/`go vet` 全绿；针对原复现路径重跑确认消失；复核 diff 确认没有改到无关行为。
10. **记录根因（Document）**：commit message 写清「现象 → 根因 → 修复 → 如何验证」，方便未来回溯，**别只写 `fix bug`**。

### 10.2 常见后端 BUG 模式速查（读码时对号入座）

| 症状 | 常见根因 | 正确修法 |
|------|----------|----------|
| 偶发 panic / 500 | nil 指针、空 map/切片访问 | 判空 + 正确零值处理 |
| 数据重复/丢失 | 无唯一约束、先查后插 | 唯一索引 + 幂等 |
| 翻页重复/漏行 | 排序不稳定 | `sort_by` + `id` 兜底 |
| 偶发错数据 | 竞态、非原子读改写 | 事务/锁/条件更新 |
| 数据改一半 | 事务范围错、缺 `Commit/Rollback` | 收进同一事务 |
| 连接耗尽/卡死 | `rows` 未关、池未配、慢查询 | `defer Close` + 配池 + 索引 |
| 注入/越权 | 拼 SQL、缺归属校验 | 参数化 + 每个 handler 校验 |
| 报错但不影响功能 | 错误被吞（`_ =`、空 catch） | 正确处理或显式忽略 |
| 时区/日期错 | 未统一 UTC、字符串比较日期 | 统一时区与时间类型 |

## 11. 回归防线（测试纪律）

- **必测三类**：正常路径、边界（空/超长/越界/重复）、异常（权限/并发/失败）。
- **并发与竞态**：用 `-race`（`go test -race`）跑；原子认领、幂等这类必须并发测试，单线程测不出来。
- **安全回归**：越权、注入、脱敏、限流都写成可重复用例。
- **证据优先**：宣布「修好了」必须给出命令输出（测试通过、接口返回、日志无 panic），**不凭感觉**。
- 集成测试用独立测试库（串行跑包），避免共享库互相污染。

## 12. 代码质量（Go 惯例）

- 命名：方法名表达意图（`ClaimPendingJob` 而非 `Update`）；错误变量 `ErrXxx`；`xxxID` 不写 `xxxId`。
- 短函数、单一职责；避免深嵌套（卫语句提前 return）。
- 常量/魔法值提出来；不重复造轮子（分类/枚举统一托管）。
- `go fmt` / `go vet` 必须干净；`gofmt -l` 无输出。
- 提交遵循 Conventional Commits（`fix(handler)/feat(service)/perf(repo)/refactor(...)`），scope 精确到层。

---

## 13. 禁止事项

| ❌ 禁止 | 原因 |
|--------|------|
| 不读代码就改 | 破坏既有契约/埋新雷 |
| 症状补丁（吞错、sleep 等竞态、特判错误值） | 根因未解，复发且更难查 |
| 修复时顺手大重构 | 无法区分「修复」与「引入」，回归难定位 |
| `SELECT *`、字符串拼 SQL、透出堆栈 | 性能/注入/信息泄露 |
| 错误静默丢弃（`_ = err`） | 线上问题不可见 |
| 并发场景用「先查后插」无唯一约束 | 必产生重复数据 |
| 修完不写回归测试、不验证 | 「修好」无从证明，极易复发 |
| 改一个 BUG 不排查同模式其它位置 | 按下葫芦浮起瓢 |
| 乱加缓存/协程优化 | 引入陈旧数据与竞态新 BUG |

## 14. 完成定义（Definition of Done）

交付一个后端功能或一个 BUG 修复，必须同时满足：

- [ ] 分层不越界：handler/service/repository 职责清晰，无跨层调用
- [ ] 接口契约明确：参数校验、错误码、分页/幂等/并发安全齐备
- [ ] 安全默认达标：鉴权/越权校验/参数化/脱敏/限流/安全头
- [ ] 数据一致性：事务边界正确，唯一约束兜底，删除完整性
- [ ] 性能不劣化：索引到位、无 N+1、连接正确关闭、池配置合理
- [ ] 错误不吞、细节不泄、日志脱敏、有指标/日志可观测
- [ ] BUG 已复现、已定位根因、已最小修复、已排查同类问题、已写回归测试
- [ ] `go fmt` / `go vet` / `make test`（含 `-race`）全绿，有命令输出佐证
- [ ] 原复现路径重跑确认修复，diff 复核无无关改动，commit 记录了根因与验证
