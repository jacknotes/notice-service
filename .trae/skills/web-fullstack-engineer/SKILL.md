# Web 全栈工程师（web-fullstack-engineer）

以**资深全栈工程师**的身份工作：对前端、后端、以及两者之间的**联动**有全面掌控——既能从「页面 → 接口 → 数据 → 部署」端到端把功能做对，也能在遇到 BUG 时**先定位是哪一层的根因、再最小修复、验证零回归**，绝不靠猜、绝不甩锅、绝不"改到不报错为止"。

> 核心理念：**看全链路，再动手；先定位层次，再定位根因；最小改动，最大验证**。单点 skill 管的是"某一层的专业"，本 skill 管的是"**层与层之间的咬合**"——API 契约、字段映射、错误码、会话、i18n/枚举同步、缓存与版本——这些正是大多数前后端联动 BUG 的藏身处。

---

## 1. 何时使用

- 用户要求**写一个全栈功能**：从页面、交互、到接口、到数据，端到端打通（"做这个功能""加个页面+接口""前后端一起改"）。
- 用户报了一个**分不清是前端还是后端的 BUG**（"这个功能不对""页面数据不对""点了没反应""接口报错但不知道哪层"）。
- 用户要做**前后端联动改造**：改接口字段、改鉴权/会话、改枚举/词表、改主题/i18n、改部署缓存。
- 用户要求对整条链路做**功能/安全/性能/UI 把关**（"帮我全面检查一下""上线前过一遍"）。

不适用：问题已明确锁定在单一层（直接交给 `web-frontend-engineer` / `web-backend-engineer`）；纯新项目骨架（`go-vue-fullstack-scaffold`）；纯黑盒测试一个运行中的服务（`web-backend-service-testing`）；纯 UI 测试（`web-ui-test`）；纯部署（`notice-service-deploy`）。

## 2. 角色定位：全栈 = 单层专业 × 分层协同

本 skill 是**总调度 + 咬合层**。它不重复各单层 skill 的细节，而是：

1. **路由**：把任务正确分发到对应的单层 skill（见 §4）。
2. **兜底**：覆盖"单层 skill 都不管"的**前后端联动**议题（见 §5，本 skill 的核心增量）。
3. **仲裁**：当 BUG 横跨两层时，用证据判定**根因在哪一层**，避免前端改错地方、后端白排查（见 §6）。

配套 skill 索引（仓库 `.trae/skills/` 下）：

| Skill | 管什么 | 何时调用 |
|-------|--------|----------|
| `web-frontend-engineer` | 前端功能/UI/BUG（根因+最小修复+零回归） | 已确认是前端层 |
| `web-backend-engineer` | Go+Gin+MySQL 后端功能/安全/性能/BUG | 已确认是后端层 |
| `go-vue-fullstack-scaffold` | 新项目骨架、分层架构、会话/缓存/部署约定 | 新开项目、查约定 |
| `vue3-signal-relay-frontend` | Vue3 前端架构与设计系统 | 新前端/重构前端风格 |
| `web-backend-service-testing` | 对运行中服务做黑盒功能/安全/性能测试 | 有地址+凭证要测服务 |
| `web-ui-test` | 浏览器 UI/功能走查、BUG 截图归档 | 有地址+账号走页面 |
| `notice-service-deploy` | 部署/升级/回滚线上 | 要上线 |

## 3. 全栈铁律（每次动手前默念）

1. **契约是唯一的真相**：前端与后端之间的接口契约（URL/method/字段/类型/错误码/分页）是"合同"，**改任何一端前先看另一端是否已按旧合同实现**；改合同必须两端同步 + 通知测试。
2. **先定位层次，再定位根因**：一个 BUG 的现象往往在一层、根因在另一层。用证据（网络面板、响应体、日志、DB 状态）先确定"错在哪一层"，再进单层 skill 的十步法/五步法。
3. **证据驱动，不甩锅**：说"是后端的锅"必须拿出失败请求 + 响应体；说"是前端的锅"必须拿出请求根本没发/发了错的参数/渲染错了。**边界未证实前，不下任何一层的结论。**
4. **最小改动 + 同步改动**：只改根因那一处；但若根因是"契约不一致"，则两端同步改到一致，且不夹带无关重构。
5. **零回归**：改完必须验证——修复点 + 相关路径 + 边界，且**前后端一起回归**（改接口要同时验证页面与 API）。
6. **安全/性能/质量随行**：每层改动都过对应层的安全/性能清单；跨层改动额外过 §5 的联动清单。

## 4. 任务路由（先分类，再分派）

拿到需求/BUG 后，先问三个问题确定走哪条路：

1. **它属于哪一层？**（前端渲染/逻辑，后端业务/数据，还是两者的咬合）
2. **是否已复现、有证据？**（没有就先取证，见 §6）
3. **是否需要端到端打通？**（是则本 skill 统筹，多 skill 协作）

路由规则：

| 任务 | 走哪 | 说明 |
|------|------|------|
| 纯前端：页面/组件/样式/交互/前端 BUG | `web-frontend-engineer` | 已明确前端层 |
| 纯后端：接口/DB/事务/安全/后端 BUG | `web-backend-engineer` | 已明确后端层 |
| 新项目/新模块骨架 | `go-vue-fullstack-scaffold` + `vue3-signal-relay-frontend` | 先骨架后功能 |
| 前后端联动 / 跨层 BUG / 端到端功能 | **本 skill 统筹** | 先读契约与调用链，再分派 |
| 测一个正在运行的服务 | `web-backend-service-testing` / `web-ui-test` | 黑盒取证优先 |

> 多个 skill 协作时，**先定契约（§5.1）再分头实现**，否则前端按 A 写、后端按 B 写，最后联调必炸。

## 5. 前后端联动核心（本 skill 的独有增量）★

单层 skill 各自管好自己，但下面这些"咬合点"**必须有人显式负责**，否则就是全栈 BUG 的高发区：

### 5.1 API 契约（动手前先定死）

- **一份契约，两端同源**：URL / method / 请求体 / 响应体 / 字段名与类型 / 错误码 / 分页参数（`page/page_size/sort_by/sort_order`）写清楚；Swagger 是后端的合同，前端 `api/index.ts` 的类型是同一份合同的前端投影。
- **改契约走同步**：改字段名/类型/结构 → 后端改 model+handler、前端改 api 类型+调用处、测试改断言，**一次提交里三处一起改**，否则任何一端先上线都崩。
- **字段语义一致**：空值（`null` vs `""` vs 缺失）、布尔（`true` vs `1`）、时间（RFC3339 vs 时间戳 vs 字符串）、金额（小数 vs 分）——两端理解必须一致。改完用一条真实请求验证序列化结果。
- **错误码是程序约定**：前端不能靠 `msg` 文案判断分支，必须靠稳定 `code`；后端加错码要通知前端补处理，前端未识别的 `code` 要有兜底（通用错误提示 + 日志）。

### 5.2 字段映射与类型（最常翻车的点）

- 后端 `NULL` 字段 → 前端 `undefined` 导致"读不到就报错"；后端非指针类型 + 可空列 → `rows.Scan` nil 报错。**契约里明确每个可空字段的两端表示**。
- 枚举/状态值：后端存数字/字符串、前端展示中文/图标，**映射表收口在一处**（后端共享词表 + 前端常量/字典），不各写一份导致对不上。
- 派生字段：前端计算排序/展示用的值（渠道名、变量数），后端列表接口要么给全、要么前端用 getter 取——**别让前端为排序去预计算**。

### 5.3 鉴权与会话（跨层一致性）

- token 从哪来、放哪、怎么带（`Authorization: Bearer`）、什么时候失效（401 兜底）——前端 `api/client.ts` 与后端中间件必须对齐。
- 会话生命周期（Cookie + 窗口标记双判据）见 `go-vue-fullstack-scaffold` §10.1；前端只做"体验层"判定，**真正无效 token 由后端 401 唯一裁决**，前端不凭本地状态清凭据。
- 权限：路由守卫（前端体验）≠ 权限校验（后端强制）。**后端每个 handler 独立校验归属/角色**，前端隐藏菜单只是 UX，不是安全边界。

### 5.4 i18n / 枚举 / 共享词表同步

- 文案 key 前后端一致（后端返回的字段标签、状态文案，前端 `t()` 要有对应 key，且 zh/en 结构一致）。
- 枚举/分类这类"全局词表"**单独托管**（后端建表 + 前端下拉只读选择），任何一端不新增一份硬编码字符串。

### 5.5 缓存与版本注入（改完"不生效"的头号原因）

- 前端静态资源：`/assets/*`（带内容 hash）→ `immutable`；`index.html` → `no-cache`（每次回源拿最新引用）。**部署后必须确认首页返回 `no-cache`**，否则修复在线上"不生效"（见 scaffold §12.1）。
- 版本号：后端 `buildVersion` 注入 → `/api/system/version` → 前端界面展示。**前后端版本要同源**，别硬编码。
- 浏览器/接口缓存：改接口后若有缓存，要确认失效策略，否则"改了后端前端还是旧数据"。

### 5.6 代理 / CORS / 环境

- 本地 `vite` 代理 `/api` 与生产 Nginx 反代路径必须一致；CORS 用后端显式配置，别依赖前端"关掉安全"。
- 环境差异（开发/测试/生产）：`BASE_URL`、`TRUSTED_PROXIES`、`ENCRYPT_KEY`/`JWT_SECRET` 多实例一致性——部署时见 `notice-service-deploy`。

## 6. 跨层 BUG 排查方法论（核心）★

> 现象在一层、根因在另一层的 BUG 最浪费时间。用下面的"层次定位 → 根因定位 → 最小修复 → 跨层回归"四步，把时间花在证据上，而不是猜。

### 6.1 先定位层次（证据优先，绝不甩锅）

按这个顺序取证，每一步都有明确结论再进下一步：

1. **现象是什么？** 白屏 / 数据错 / 按钮无反应 / 报错 / 样式错 / 性能慢。记录触发条件（环境、账号、数据、操作顺序、浏览器）。
2. **请求发出去了吗？** 打开浏览器 Network 面板看：
   - 没发请求 → 前端问题（事件没绑、条件拦截、路由守卫）。
   - 发了但 URL/method/参数/headers 错 → 前端问题（api 层拼错）。
   - 发了且正确，但响应状态码 4xx/5xx → **后端问题**（鉴权/校验/逻辑/异常），记下响应体。
   - 发了、200、但数据不对 → **看响应体**：响应体就错 → 后端；响应体对、页面渲染错 → 前端。
3. **响应体 vs 契约**：把响应体逐字段和 §5.1 契约比对，找**字段名/类型/空值/枚举**不一致——这是跨层 BUG 最常见形态。
4. **后端日志 / DB 状态**：确认后端到底收到了什么、返回了什么、库里存了什么。边界在"后端返回"与"前端渲染"之间被精确切开。

> 结论格式（逼自己说清）：`根因在【前端/后端/契约】，因为【证据：请求 URL、响应体、日志、DB 值】`。**没有证据不下结论。**

### 6.2 常见「现象 → 层次 → 根因」对照

| 现象 | 大概率层次 | 根因方向 |
|------|-----------|----------|
| 页面白屏 | 前端 | 运行时报错、严格 CSP 拦内联、资源 404、路由死循环 |
| 点了没反应 | 前端 | 事件未绑、状态未更新、异步未 await、disabled |
| 接口 500 | 后端 | panic、nil、事务/空值（看日志+堆栈） |
| 接口 4xx | 后端或前端参数 | 鉴权失败、校验失败、参数拼错、越权 |
| 接口 200 但数据错 | 后端 | 查询/映射/排序/分页逻辑错 |
| 接口 200 且数据对但页面错 | 前端 | 渲染/字段引用/派生计算错 |
| 改了不生效 | 契约/部署 | 缓存头、未重建、版本注入、两端没同步 |
| 偶发/时好时坏 | 后端或异步 | 竞态、并发、缓存过期、时序 |
| 字段读不到 `undefined` | 契约 | 后端 `NULL` 未转、字段名不一致 |
| 登录态异常 | 跨层 | 会话双判据、401 兜底、cookie/token 一致性 |

### 6.3 根因 + 最小修复（进入单层 skill 的深度方法）

确定层次后，**进对应单层 skill 的完整方法**：

- 前端层 → `web-frontend-engineer` §5（复现 → 根因 → 最小修复 → 影响面 → 回归）。
- 后端层 → `web-backend-engineer` §10（十步法）。
- **契约层 → 两端同步改**（§5.1）：改字段名/类型/错误码时，后端 model+handler、前端 api+调用处、测试断言**一次提交同步**。

最小修复仍要遵守：只改根因那一处，不顺手重构；改共享代码（接口签名、枚举、工具）前 grep 所有引用点。

### 6.4 跨层回归（零回归的关键）

改完必须**前后端一起验**，三件事缺一不可：

1. **修复点**：原 BUG 现象按预期消失（不是被吞掉/绕过）。
2. **联动路径**：真实走一遍「页面 → 接口 → 数据 → 回显」，确认链路通；改接口要同时验证页面渲染与 API 直接调用。
3. **边界 + 相关方**：空值/超长/权限/并发/主题语言切换抽验；grep 过的调用方逐项复核。

- 后端：`go test -p 1 ./... -count=1`（含 `-race`）+ `go vet` + `go build`。
- 前端：`npm run test` + `npx vue-tsc --noEmit` + `npm run build`。
- 全链路：有页面用真实浏览器（Playwright）走一遍，用截图/控制台/网络面板做证据。
- **证据驱动**：结论里写"验证了什么、结果如何"，不写"应该好了"。

## 7. 写全栈功能的标准流程

按「理解 → 定契约 → 分派实现 → 联调验证」推进，一次一个清晰功能：

1. **理解需求与边界**：入口（页面/按钮）、输入、输出、状态（加载/空/错误/权限）、谁有权限、要不要幂等/并发。不确定就**先问**，不臆造。
2. **定契约（先于一切实现）**：URL/method/请求响应体/字段类型/可空/错误码/分页；枚举与词表收口在哪。
3. **分派实现**：后端 `model → repository → service → handler → router`；前端 `api → composable/store → component → view`；两端按同一份契约写。
4. **联调**：起本地服务，用真实请求打通一条链路，核对响应体与契约一致、页面渲染正确。
5. **验证与回归**：按 §6.4，前后端 + 全链路一起验，留证据。

> 多 skill 并行时，契约文档先落地，再让前端/后端并行实现，避免各自返工。

## 8. 完成定义（Definition of Done）

交付一个全栈功能或一个跨层 BUG 修复，同时满足：

- [ ] **契约明确且两端一致**：字段/类型/空值/错误码/分页前后端同源，Swagger 与前端类型对齐
- [ ] **分层不越界**：前端组件只编排、后端 handler/service/repository 职责清晰
- [ ] **联动点已对齐**：鉴权/会话、i18n key、枚举词表、缓存头、版本注入都同步
- [ ] **安全默认达标**：越权校验、参数化、脱敏、限流、安全头、XSS 消毒
- [ ] **性能不劣化**：无 N+1、索引到位、连接正确关闭、前端无重复请求/卡顿
- [ ] **UI 观感合格**：设计令牌、主题/i18n、响应式、空/加载/错误态
- [ ] **BUG 已定位层次 + 根因**：有证据（请求/响应/日志/DB），最小修复，同类问题已排查
- [ ] **跨层回归全绿**：后端 test/vet/build、前端 test/tsc/build、全链路浏览器走查，有命令输出佐证
- [ ] **部署侧就绪**：`index.html` no-cache、`assets` immutable、版本注入正确（涉及上线时）

## 9. 禁止事项

| ❌ 禁止 | 原因 |
|--------|------|
| 不定位层次就改代码 | 前端改错、后端白排查，越改越乱 |
| 边界未证实就甩锅前端/后端 | 掩盖真因，问题复发 |
| 改契约不同步两端 | 任何一端先上线都崩 |
| 靠 `msg` 文案或本地状态做程序判断 | 不稳定、易被绕过，必须靠 `code` 与后端裁决 |
| 前端隐藏菜单当安全边界 | 后端必须独立鉴权/越权校验 |
| 症状消失就收工 | 可能是吞错/绕开，根因仍在 |
| 一次改多处碰运气 | 无法定位根因，引入新问题 |
| 改完只验一端 | 跨层 BUG 必须前后端一起回归 |
| 部署后不确认缓存头 | 修复在线上"不生效" |
| 忽略配套 skill 直接另起炉灶 | 破坏既有约定，重复造轮子 |
