### 0.3 总体结论

**不建议以当前状态发布。** 本次 52 个提交在工程正确性上有明显进步（队列 CAS + 续租、2FA pending 令牌隔离、登录防枚举、重置令牌哈希化、容器非 root、迁移锁修复），但**同时引入了 1 个凭据失守级缺陷和 2 个「安全承诺名不副实」级缺陷**，且存在一个**用户按产品自身引导操作即静默失败**的 blocker。

核心判断：这批变更的**代码实现质量高于其验证与文档质量**。多个新增的安全机制在「最常用的运维路径」上被绕过或只做了一半（TOTP 加密、STRICT_SECRETS、防重放），失败模式普遍是**静默通过**而非报错——这比没有该机制更危险，因为它给出虚假的安全保证。

### 2.1 【BLOCKER】B-1 农历 `term` 快捷项与节日名静默失效（合并 M1）

- **共同命中**：**性能 / 产品**
- **出处**
  - 性能：`perf.md` P1（high）→ `internal/scheduler/lunar_schedule.go:26-41, 80-96, 115-142`、`scheduler.go:74-119`、`service/queue.go:333-352`、`cmd/server/main.go:195-206`、`service/task_service.go:120-129, 186-192`
  - 产品：`product.md` P1（blocker）→ `web/src/views/Tasks.vue:812`、`internal/scheduler/lunar_schedule.go:100-110`、`internal/service/task_service.go:413-423`、`web/src/views/Tasks.vue:876-882`
- **严重度收敛**：性能 **high** / 产品 **blocker** → **blocker**（取最高）。理由：判据不是「代码 bug 大小」，而是「用户按产品自身提供的快捷引导操作 → 静默得到永不触发的任务 → 漏发通知且**零可观测信号**」。性能侧定 high 是因为它衡量的是开销，未把「功能静默失效」计入。
- **证据强度**：**【实测】**（双方独立实测）+ **【静态确认】**
- **归属**：**存量缺陷被本批放大**（captain 裁定 1，保留正文；详见下方「归属说明」）

**问题机制（合并双方）**

1. **字符串不匹配【静态确认】**：快捷项表达式为 `@lunar term 中秋 09:00`（`Tasks.vue:812`，实测确认该行存在），而 `lunarFestivals` 的键是 `中秋节`（`lunar_schedule.go:106`，实测确认）。`term` 的节气回退分支用 lunar-go 的 `GetCurrentJieQi()`，其 24 节气名不含「中秋」——**两条路径都命中不了**。
2. **性能后果【实测】**：命中不了的名字会走完全部 8 年 × 370 天扫描才返回零值。实测单次 `Next()`：

   | 表达式 | 单次耗时 | 分配 | 结果 |
   |---|---|---|---|
   | `@lunar term 中秋 09:00`（快捷项） | **336 ms** | **92 MB** | **零值（永不触发）** |
   | `@lunar term 不存在 09:00` | 345 ms | 92 MB | 零值 |
   | `@lunar term 清明 09:00` | 36–68 ms | 10–20 MB | 命中 |
   | `@lunar term 立春,清明,夏至,冬至 09:00` | ~185 ms | ~54 MB | 命中 |
   | `@lunar monthly 15 09:00` | 1.0–1.5 ms | 114 KB | 命中 |

3. **阻塞全体派发【静态确认】**：`robfig/cron` 的 run loop 是**单 goroutine**，每次触发后在同一循环内同步执行 `e.Next = e.Schedule.Next(now)`（已核对 `cron/v3@v3.0.1/cron.go:275`）。因此 `LunarSchedule.Next` 的 36–336 ms 会阻塞**所有任务**的派发。
4. **启动路径叠加【实测/推断】**：`main.go:195-206` 对每个 cron 任务先 `RefreshNextRun`（1 次 `Next`）再 `RegisterTask`（`cron.AddFunc` 内部再 1 次 `Next`）。性能侧估算 100 个节气任务 ≈ 2×100×68 ms ≈ **13.6 s 启动延迟**（此为**估算**，未实测整机启动）。
5. **产品后果【实测】**：保存返回 **200 成功**（`task_service.go:413-423` 只判断 `Parse` 是否报错；`term` 分支仅校验 `HH:MM` 与名字非空）；前端 `formRules` 对 `cron_expr` 无自定义校验器；列表把空 `next_run_at` 渲染为中性的 `—`（`Tasks.vue:876-882`），与「api 任务/停用任务」的空值视觉完全一致，**无法区分「正常无下次」和「配置错了」**。
6. **同类问题范围（产品侧扩大）【实测】**
   - 5 个 UI 快捷项中 `monthly 1/15`、`yearly 1 1`、`term 清明` **有效**；`term 中秋` **零值**；`term 中秋节` **有效**。

- **证据强度**：**【静态确认】**（两处 SQL 与一处传参已由合成人逐一读码确认，见附录 B）
- **归属**：**本次新引入**【实测/静态确认】：`totp_secret_enc` 列在 v2.0.0 **不存在**（`git show v2.0.0:internal/repository/user_repo.go` 无该字段；本次新增迁移 `020_totp_replay_and_encrypted_secret.sql`）。

**破口 ①：`ForceEnable2FA` 明文落库**

管理员通过 `POST /api/users/{id}/2fa-enable`（`router.go:188`）或批量 `POST /api/users/batch-2fa-enable`（`router.go:186`）为用户开启 2FA 时，`ForceEnable2FA` 写库的第一个实参（`secretEnc`）**硬编码为空串**（已读码确认 `user_service.go:309`），于是种子落到 `totp_secret` 明文列，`totp_secret_enc` 保持 NULL。

攻击者取得 DB 只读权限（备份泄露、只读账号、误导出 dump）后即可获得全部被强制开启 2FA 用户的种子，离线生成任意时刻动态码，结合口令即可完整绕过 2FA。

**安全属性倒挂**：用户**自助开启**的路径（`auth_service.go:290-299` 的 `storeTOTPSecret`）从写入起就是加密的，而管理员**批量强制开启**（更常见的合规运维操作）反而是明文——越是被组织统一管理的账号，保护越弱。

**破口 ②：升级路径不清明文列**

`SetTOTPSecretEnc` 的 SQL 为 `UPDATE users SET totp_secret_enc=? WHERE id=?`（已读码确认 `user_repo.go:226-230`），**明文列原封不动**。因此被强制开启 2FA 的用户首次登录成功、走 `!encrypted && s.cipher != nil` 分支升级后，该行**同时**保存同一份种子的明文与密文，且此后任何一次登录都不会再清理明文列。

`DisableTOTP` 同样只置空 `totp_secret`，**不清 `totp_secret_enc`**（已读码确认 `user_repo.go:241-243`），已停用账号的种子材料长期驻留 DB，违反数据最小化。

**为何「修其一不足以闭环」**：即便修好 ①（让 `ForceEnable2FA` 直接写密文），只要 ② 的升级路径不清明文列，历史数据的升级也只是「多存一份」而非「消除明文」；反之只修 ②，① 仍会让新写入的种子从第一天起就是明文。

**修复建议**

1. `UserService` 注入 `crypto.Cipher`（或复用 `AuthService.storeTOTPSecret` 的加密逻辑），`ForceEnable2FA` 改为加密写入。
2. `SetTOTPSecretEnc` 改为 `UPDATE users SET totp_secret_enc=?, totp_secret=NULL WHERE id=?`（升级即消除明文）。
3. `DisableTOTP` 同时置空 `totp_secret_enc` 与 `totp_last_counter`。
4. 在 `SetTOTP` 层 fail-closed：拒绝 `secretEnc == "" && secretPlain != ""` 的生产调用，把「明文降级」限制在测试可显式构造的构造器里。
5. 把「两列至多一列非空」做成写入层不变量，并补集成测试断言升级后 `totp_secret IS NULL`。

### 2.4 【HIGH】H-2 SMTP 认证协商引入明文降级与 CRAM-MD5 优先

- **出处**：`security.md` S-5 → `internal/channel/email.go:104-132`（`authByExtensions`）、`:116-120`、`:135-148`（`cramMD5Auth`）、`:84-87`
- **严重度收敛**：安全 **high**
- **证据强度**：**【静态确认】**（分支顺序与摘要算法读码确认；无中间人实测）
- **归属**：**本次新引入**【实测】：`CRAM-MD5` 在 v2.0.0 的 `email.go` 中**不存在**（`git show v2.0.0:internal/channel/email.go` 无该字符串；本次 +79 行）

**问题机制**

1. **LOGIN 在 TLS 前就被选中**：`authByExtensions` 的分支顺序只依据服务器宣告的 `AUTH` 扩展，**没有**先判断 `secure`。若渠道配置 `allow_insecure=true`（内网明文中继，官方支持的场景）且服务器宣告 `LOGIN`，用户名/口令以 base64（等价明文）走网络——分支里没有任何日志或拒绝，运维无法感知。
2. **CRAM-MD5 降级为 HMAC-MD5**：`cramMD5Auth` 使用 `crypto/md5`。攻击者若能在 TLS 建立前注入（如 `allow_insecure` 明文连接 + 中间人扮演 SMTP 服务器并宣告 `CRAM-MD5`），可对已知挑战做**离线字典攻击**（HMAC-MD5 无迭代、无盐）。
3. **明文连接上宣告 `CRAM-MD5` 时不再检查 `allow_insecure`**：该分支直接认证，**绕过**了 `PLAIN` 分支才有的 `secure || allow_insecure` 守卫。虽然 CRAM-MD5 不上线口令，但响应可被重放（恶意服务器可固定挑战 → 重放响应即完成认证）。
4. **未宣告 `AUTH` 时在 TLS 上回落 `PlainAuth`**：若服务器宣告了 `AUTH` 但内容为空串，`advertised` 为空 map，落到「未宣告」分支，行为与 PLAIN 相同——该路径在 TLS 上安全，但**日志缺失**使配置漂移不可见。

**影响**：邮箱授权码是长期凭据（多数服务商不支持单独吊销），一旦泄露可长期冒名发信、被用于钓鱼（借助受害组织域名信誉）。`allow_insecure` 是显式配置，但当前实现让「显式接受明文」的范围从「PLAIN 口令」**扩大到「任何认证方式的握手细节」**。

**修复建议**

1. `authByExtensions` 增加参数顺序守卫：`secure == false` 时**只允许** `CRAM-MD5`；`LOGIN`/`PLAIN` 必须 `allow_insecure=true` 且每次发送打 warning 级日志。
2. `cramMD5Auth` 换成 `crypto/sha256` 实现 CRAM-SHA256（若服务器支持），或至少在对端宣告 `CRAM-MD5` 但连接非 TLS 时拒绝。
3. 对「宣告 AUTH 但列表为空」显式返回错误，而不是回落 PLAIN。

**修复建议**

1. 服务端流式写：`rows.Next()` 边读边 `csv.Writer.Write`，每 500 行 `Flush`，让字节持续出网。
2. 导出接口单独放宽写超时：用 `http.ResponseController.SetWriteDeadline` 在 handler 内覆盖（`http.Server` 是全局的）。
3. 行数上限降到 1–2 万，或改异步导出（生成文件 + 下载令牌）。

## 3. 分视角深度分析

> 以下三节保留各视角自身的分析框架与「已确认的正面改进」，不重复 §2 的条目正文，只补**该视角独有的判断**。

### 3.1 性能视角

**审查方法**：逐 diff 走查 + 为量化 `Next()` 开销临时建 `main` 包（`.perfprobe/`）直接调用 `scheduler.NewLunarParser().Parse(...).Next(...)` 并读 `runtime.MemStats`，测后已删除。**全仓 `*_test.go` 中没有任何 `func Benchmark`**，故无现成基准可用。

**验证结果**：`go build ./...` 通过（exit 0）；`go vet ./...` 通过（exit 0）；`go test ./internal/render ./internal/channel ./internal/totp ./internal/config` 全部 `ok`；`go test ./internal/scheduler` 仅 `TestSchedulerLeasePath` 失败（`invalid connection`，本机无 MySQL，**环境缺失非代码问题**）。

**性能视角的核心判断（按影响排序）**

1. **`Next()` 计算在 cron 单 goroutine run loop 里同步执行**，这是本次最大的性能地雷。它不是一个「慢查询」，而是**阻塞全体派发**的架构性风险：任何单个任务的 `Next` 耗时都会平移所有任务的触发时刻。
2. **队列吞吐被硬编码为 `Workers / PollInterval`**（默认 4 job/s，见附录 A-2），且 worker 忙时 tick 被合并丢弃——30 s 的发送会合并掉 29 个 tick。**这条虽是既有问题，但本次新增的续租心跳（`queue.go:183-216`）恰恰是为长发送兜底，说明该成本已被感知而根因未处理。**
3. **列表类接口普遍「先 COUNT 再分页」+ 新增排序列无索引**：审计日志（`LIKE '%kw%'` + 新排序，本次新增）、发送日志（`status/retry_count/category` 排序，既有）都会退化为全表扫描 + filesort。
4. **前端已加竞态保护，但只加了一半**：Logs/Dashboard 有 `loadSeq`，审计页（本次新增排序）没有；任务页仍是「整表拉取 + 每次按键全量重排」，且比较函数每次新建 `Intl.Collator`（实测 4000 行排序：`localeCompare` 11.1 ms vs 复用 `Collator` 6.7 ms，约 1.65×）。

**性能视角认为「做得好」的部分**：队列的 CAS + 续租 + 崩溃计入 attempts（`send_job_repo.go:100-135, 188-205`）在正确性上显著优于 v2.0.0；`recoverLoop` 对 `interval < time.Second` 做了兜底；日志页与仪表盘补了 `loadSeq` 竞态守卫。

**复核确认得到修复的正面改进（不重复计入发现）**

- **2FA pending 令牌隔离**：`middleware/auth.go:24-29` 拒绝 `claims.TwoFA` 令牌访问业务 API——**这是本次最关键的一处修复**（此前 2FA 可被跳过）。
- **登录防枚举**：账号不存在与账号禁用两条路径都跑等价 bcrypt（`auth_service.go:227-242`），`dummyBcryptHash` 为公开口令哈希（非机密），时序差被抹平；`loginBucket` 用 `username|ip` 复合桶避免「知道用户名即可锁死受害者」的 DoS。
- **TOTP 防重放（标准场景）**：`MatchingCounter` 在 ±1 步窗口内命中（`totp.go:75-92`），`validateTOTPWithReplay` 要求 `counter > lastCounter` 且写库失败即拒绝；`Enable2FA`/`Disable2FA` 有意不消耗计数器（避免「启用后 30s 内登录被误拒」），取舍合理。**并发场景的缺口见 M-4。**

**安全视角的元判断**：本次变更的**安全设计意图普遍正确，但落地时有 5 处「看似校验、实际放行」**（H-1 及其 3 个附加项、M-3、M-4）。这类缺陷的共同特征是**失败模式为静默通过**——不报错、不告警、日志无痕迹，因此无法通过「服务是否正常启动」这类信号发现。建议把「安全开关必须有可观测的失败信号」作为后续 review 的固定检查项。

**安全视角的排除项（重要，避免误判）**

- `forgot-password` 与 webhook 限流在 DB 故障时 **fail-open**（`auth_handler.go:238`、`webhook_handler.go:62-63`），这是**有意为之**且注释明确（登录/触发本身依赖 DB），**不计为缺陷**；但建议 fail-open 时至少打一条 error 级日志以便告警。

- `gofmt -l` 列出大量文件，已定位原因为 Windows 工作区检出为 CRLF，`gofmt -d` 差异全部是行尾符，**非缺陷**（`.gitattributes` 已保证入库为 LF）。

### 3.3 产品视角

**审查对象**：自托管运维者与管理员（不是终端收件人）。

**产品视角的严重度定义**（与安全/性能不同，故定级有差异）：**blocker** = 用户按界面引导操作即得到错误结果且无任何提示；**high** = 主要功能对一类用户静默失效或升级会打断既有部署；**medium** = 明显误导/困扰但有绕过路径；**low** = 文案与一致性瑕疵。

**产品视角的核心判断（Top 5，按产品影响排序）**

1. **B-1（blocker）· 农历「中秋」快捷按钮产出永不触发的任务，且保存静默成功。** 修复要点不在改一个字符串，而在补齐**三道产品护栏**：节日名白名单校验（保存即报错并列出可用名字）→ 零值触发点警告 → 列表把「无下次触发」显示为异常。
2. **H-4 + 附录 A-4（high）· 「一键部署」这条最主力的上手路径有两处硬伤**：镜像 tag 策略自相矛盾（文档说 `latest`，文件钉 `-g<sha>`）、端口写错（README 8080 / compose 8081，见附录 A-4）。前者让 `pull && up -d` 升级静默无效；后者让新用户在第一分钟连不上。**自托管产品的口碑主要取决于首次部署成功率。**
3. **H-1（high）· `STRICT_SECRETS=1` 的承诺是假的。** 这比没有严格模式更危险——用户会因为「启动成功」而确信自己已按安全要求配置。修复很小，但产品含义是「**文档承诺必须由代码兑现**」。
4. **M-7 + M-10 + M-11 + H-5（同一主题）· 本次交付的几个「状态开关」缺少失效可见性**：模板停用后关联任务毫无提示（M-7）、`next_run_at` 空值无法区分正常与故障（M-10）、「合法但永不触发」保存后只报成功（M-11）、备份导入把模板一律写成停用（**H-5，high，原产品 P12；经 captain 裁定恢复正文，归属「存量缺陷被本批放大」**）。共同模式是「**配置生效了，但用户看不出它导致了什么**」。H-5 尤其致命：它让**什么都没做错、只是迁移了环境**的运维者在无任何告警的情况下失去全部通知能力。产品上应统一为一条原则：**任何让任务停止投递的状态变更，都必须在该任务所在列表上留下可见标记**；导入路径必须逐字段还原状态。
5. **M-12（medium）· CHANGELOG 的 `[Unreleased]` 为空**，52 个提交的重大变更零记录，其中 `STRICT_SECRETS`（升级后可能启动失败）、MySQL 8.0、登录态窗口化（关浏览器即登出）三项会直接改变升级体验。

**产品视角认为「做得好」的部分**：本次交付的批量操作体系（启停/改分类/改渠道/改接收地址）覆盖了运维日常高频动作；任务表新增「下次触发时间」「通知模板」两列直接回应了「这个任务什么时候发、用哪个模板」的核心疑问（虽然引入了 L-13 的窄屏问题）；农历快捷选择器方向正确（只是内容有错）；渠道测试按钮、模板实时预览等交互质量不低。

- **问题机制**：一次任务有 K 个收件人就有 K 次 `dial → (TLS) → EHLO → AUTH → MAIL/RCPT/DATA → QUIT`，连接完全不复用。50 个收件人 ≈ 50 次 TLS 握手 + 50 次认证，单次发送可达数十秒。**本次新增的续租心跳正是为这种长发送兜底——说明该成本已被感知，但根因（无连接复用）未处理。**
- **修复建议**：同一渠道一次连接内多收件人（`smtp.Client` 支持多次 `Mail/Rcpt`）；加连接池（按渠道 ID 缓存 `*smtp.Client`，带空闲超时与健康检查）；把「已成功列表」持久化，避免 job 级重试整批重发（见 A-17）。

### A-16 批量启用/删除任务先 `repo.List()` 全表加载 — 性能 P7（原定 medium）

- **出处**：`internal/service/task_service.go:234-260, 209-231`、`internal/repository/task_repo.go:90-92`
- **v2.0.0 实况（git 复核）**：v2.0.0 的 `BatchToggle` **完全相同**（`all, err := s.repo.List()` 已存在）。
- **问题机制**：为判断「选中的 id 里哪些是 cron 任务」，把**全部任务**（含 `variables`/`receivers`/`allowed_ips`/`channel_ids` 等 JSON 列）读进内存建 map；批量操作本应只处理选中的几十条。任务数上千时，一次「批量禁用 3 条」= 一次全表 SELECT（上千行 × 22 列）+ 上千次对象分配 + 全量 map 构建。
- **修复建议**：新增 `TaskRepo.ListCronByIDs(ids)`，只 `SELECT id, cron_expr ... WHERE id IN (...) AND trigger_type='cron'`；`List()` 增加列裁剪版本。

### A-17 job 级重试会重发已成功的渠道/收件人 — 性能 P14（原定 low）

- **出处**：`internal/service/notification_service.go:105-149`、`internal/repository/send_job_repo.go:146-167`
- **v2.0.0 实况（git 复核）**：`next_retry_at` 与退避机制在 v2.0.0 **已存在**。
- **问题机制**：一个任务绑 3 个渠道、10 个收件人，第 1 个渠道失败 → 整 job 重试 → 已成功的渠道/收件人被重复投递，最坏 3 次 × 13 个目标 = 39 次发送，其中 36 次是重复。对接收方是骚扰，对服务是 3 倍的第三方调用配额与 SMTP 连接成本。代码注释已声明「重试会重发成功的渠道，这是 job 粒度重试的已知取舍」。
- **修复建议**：把「发送单元」从 job 粒度下沉到（渠道 × 收件人）粒度，或成功目标写 `task_logs` 后重试时跳过已成功组合；短期至少把「渠道停用/模板停用」这类永久失败与「网络失败」区分开。

### A-18 迁移 `GET_LOCK` 期间持有专用连接最长 120 s — 性能 P15（原定 low）

- **出处**：`internal/database/db.go:45-103`、`internal/database/migrations/019_users_username_active_unique_fix.sql`、`018_tasks_cron_expr_width.sql`
- **v2.0.0 实况（git 复核）**：`GET_LOCK` 在 v2.0.0 的 `db.go` 中**已存在**（本次改动是「用专用连接 + 显式判断返回值」，属修复而非引入）。
- **问题机制**：加锁到释放之间执行**全部**待应用迁移，且每条语句用同一连接串行执行。`019`/`018` 这类 `ALTER` 在中等规模表上可跑数十秒；此期间其它副本启动流程阻塞在 `GET_LOCK` 上（最长 120 s），超过即 `log.Fatalf` 退出 → 滚动发布时表现为「新 Pod 启动失败重试」。锁本身必要（防重复 ALTER），问题在「持锁粒度过大 + 启动路径无重试」。
- **修复建议**：迁移按文件粒度加锁/释放；拿不到锁时指数退避重试而非 `Fatal`；把 DDL 迁移与启动解耦（独立 `migrate` 命令/Job）。

### A-19 前端任务页整表拉取 + 每次按键全量过滤/排序，比较函数内重复创建 `Intl.Collator` — 性能 P10（原定 low）

- **出处**：`web/src/views/Tasks.vue:701-721, 725-735, 861-873`、`web/src/composables/useTablePaging.ts:34-44, 63-70`
- **v2.0.0 实况（git 复核）**：`filteredTasks` 与 `useTablePaging.ts` 在 v2.0.0 **均已存在**。
- **问题机制**：`keyword` 是 `v-model` 双向绑定，每敲一个字符都会让 `filteredTasks` 产出新数组 → `sorted` 重排全表 → `paged` 重切片。比较函数里没有复用 `Intl.Collator`，而 `localeCompare(..., 'zh-Hans-CN')` 每次调用都会解析 locale。**实测** 4000 行排序：`localeCompare` 11.1 ms，复用 `Intl.Collator` 6.7 ms（约 1.65×）。`channelNames` 对每行每渠道做线性 `find`，是 O(行 × 渠道)。
- **修复建议**：模块级 `const collator = new Intl.Collator('zh-Hans-CN')`；预建 `channelMap`/`templateMap` 改 O(1) 查表；搜索输入加 200–300 ms 防抖。

### A-20 仪表盘每次加载 5 条聚合 SQL 且无缓存，环形图每次 `load` 渲染两遍 — 性能 P12（原定 low）

- **出处**：`web/src/views/Dashboard.vue:264-291, 282, 303`、`internal/service/dashboard_service.go:51-65`、`internal/repository/task_log_repo.go:241-269`
- **v2.0.0 实况（git 复核）**：`renderDonut` 在 v2.0.0 的 `Dashboard.vue` 中**已存在**。
- **问题机制**：一次仪表盘打开 = 5 条对 `task_logs` 区间的聚合查询（2+1+1+1），默认近 7 天；没有短 TTL 缓存，切页/刷新/改日期全部重算。`COUNT(DISTINCT task_id)`、`COUNT(DISTINCT channel_id)` 各扫一遍同一区间（可合并进一条语句）。前端 `load()` 里显式 `renderDonut()` 之后，`Object.assign(stats, ...)` 又会触发 `deep` watch 再渲染一次，等于每次加载 `setOption` 两遍。
- **修复建议**：合并 `StatsRange` 为 1 条 SQL；对 `(from,to)` 加 10–30 s 内存缓存或 `singleflight`；去掉 `deep` watch 或去掉显式 `renderDonut()`（二者留一）。

### A-21 模板编辑页实时预览：每次按键全量 `marked.parse` + `DOMPurify.sanitize` — 性能 P13（原定 low）

- **出处**：`web/src/views/Templates.vue:412-419`、`web/src/components/MarkdownPreview.vue:29-31`
- **v2.0.0 实况（git 复核）**：`DOMPurify` 在 v2.0.0 的 `MarkdownPreview.vue` 中**已存在**。
- **问题机制**：`form.content_md` 是 `v-model` 文本域，每敲一个字符都会触发一次完整 Markdown 解析 + DOM 清洗 + `v-html` 重设 innerHTML。模板正文通常几百到几千字，长模板下连续输入会明显掉帧；`DOMPurify` 对整段 HTML 的遍历是主要成本。
- **修复建议**：对 `previewMarkdown` 的输入做 150–300 ms 防抖；或输入时只显示源码、失焦/点「预览」再渲染。

### A-22 发送日志列表新增排序字段无索引，每页固定 2 条 SQL — 性能 P6（原定 medium）

- **出处**：`internal/repository/task_log_repo.go:184-237, 164-180`、`internal/database/migrations/001_init.sql`
- **v2.0.0 实况（git 复核）**：`sortColumn` 白名单在 v2.0.0 中**已包含** `status`/`retry_count`/`category`（逐行对比确认完全相同），`COUNT` + 页查询 + `LEFT JOIN tasks` 亦已存在。→ 该缺陷在 v2.0.0 即成立，本次未改。
- **问题机制**：`status`、`retry_count`、`t.category` 无索引，按这些列排序时对命中行做 filesort；`category` 排序还作用在 JOIN 后的 `tasks.category` 上，JOIN 顺序不可控。每条列表请求固定 2 条语句，`COUNT(*)` 与页查询各扫一遍区间（`COUNT` 无法用覆盖索引，因 `task_logs` 有多个 TEXT 列）。
- **修复建议**：排序白名单只保留有索引列；加 `(status, sent_at)`、`(channel_id, sent_at)`、`(sent_at, id)` 复合索引；把 `tasks.category` 反范式到 `task_logs` 去掉 JOIN。

### A-23 模板 `enabled` 开关文案在列表与表单不一致（「开/关」vs「启用/停用」）— 产品 P13（原定 low）

- **出处**：`web/src/views/Templates.vue:110-111, 184-188`、`web/src/views/Tasks.vue:359`、`web/src/locales/zh-CN.json:349-350`

### A-24 前端测试在本机无法运行（jsdom 30 与 Node 20 不兼容），CI 使用同一 Node 20 — 产品 P22（原定 low）

- **出处**：`web/package.json:10`、`web/package-lock.json`（`jsdom` 30.0.1，`engines.node` 为 `^22.22.2 || ^24.15.0 || >=26.0.0`）、`.github/workflows/ci.yml:112, 121-123`
- **v2.0.0 实况（git 复核）**：`jsdom: ^30.0.1` 与 `node-version: '20'` 在 v2.0.0 **均已存在**。
- **问题机制【实测】**：`cd web && npm test` → 8 个 unhandled error（`TypeError: webidl.util.markAsUncloneable is not a function`），`Test Files no tests / Tests no tests`，退出码 1（本机 Node v20.20.2）。`npx vue-tsc --noEmit` 通过（exit 0），说明类型检查正常、测试环境不可用。`--passWithNoTests` 会掩盖「一个测试都没跑起来」这一事实。

### A-25 首屏体积 / `middleware.Auth` 每请求回查用户 / `/categories/unused` 的 N+1 — 性能视角「附：既有问题」3 条

- **出处**：`perf.md` 第 253-257 行「附：既有问题」；`web/dist` 实测、`internal/middleware/auth.go:32-41`、`internal/repository/category_repo.go:129-149`、`web/src/views/Categories.vue:272-304`
- **说明**：性能视角明确注明「本次未改动，故不计入正式发现」。三条为：
  1. **首屏体积**：本地 `web/dist` 实测 `index-*.js` 1225 KB、`Dashboard-*.js` 1023 KB（整包 `import * as echarts`，且默认落地页就是 `/dashboard`）、`index-*.css` 367 KB（`main.ts` 全量 `app.use(ElementPlus)`）。首屏约 **2.25 MB JS + 367 KB CSS**。建议 echarts 按需引入（`echarts/core` + 折线/饼图）与 Element Plus 按需自动导入。
  2. **`middleware.Auth` 每请求回查用户**：每个业务请求 1 条 `SELECT users`。本次只加了 `claims.TwoFA` 判断，未改变该开销；高 QPS 下建议 5–10 s 本地缓存（配合 `session_revoked_at` 失效广播）。

### A-26 `send_jobs` 认领查询 `ORDER BY id` 触发 filesort，缺 `(status, id)` 索引；完成清理缺 `updated_at` 索引 — 性能 P4（原定 medium）

- **出处**：`internal/repository/send_job_repo.go:76-80, 210-225`、`internal/database/migrations/002_send_jobs.sql`
- **v2.0.0 实况（git 复核）**：`ORDER BY id LIMIT`、`CleanupDoneOlderThan`、`idx_jobs_status` 在 v2.0.0 **均已存在**；`idx_jobs_updated` 在 v2.0.0 与 HEAD **均不存在**。→ 该缺陷在 v2.0.0 即成立，本次未改。
- **问题机制**：`idx_jobs_status (status, next_retry_at)` 只能过滤 `status`，`ORDER BY id` 必须对全部 pending 行做 filesort；`next_retry_at IS NULL OR ...` 的 OR 条件进一步阻止索引范围收敛。叠加 A-2 的 tick 驱动（每秒 4 次，4 副本 ×4 worker = 16 次/s），pending 积压时排序集同步膨胀。`CleanupDoneOlderThan` 的过滤列 `updated_at` 无任何索引，`LIMIT 1000` 的循环删除在「老行稀疏」时要反复全表扫描，而 `done/failed` 行占表绝大多数。
- **修复建议**：新增 `KEY idx_jobs_status_id (status, id)`，或改 `ORDER BY next_retry_at, id` 并让索引 `(status, next_retry_at, id)` 覆盖；加 `KEY idx_jobs_updated (updated_at)` 或 `(status, updated_at)`；清理改按 `id` 分页删除。

### A-27 渠道配置不校验 URL scheme，管理员可配置任意内网地址，构成 SSRF（含云元数据）— 安全 S-19（原定 medium）

- **出处**：`internal/channel/webhook.go:12`（`&http.Client{Timeout: 15s}`，无 Transport/无 scheme 限制）、`internal/channel/wechat.go:43-45`（`pushplus_url` 可任意覆盖 `endpoint`）、`internal/service/channel_service.go:58-72`（`Create` 只校验类型存在）、`:74-94`（`Update` 同样）
- **v2.0.0 实况（git 复核）**：`http.Client`、`pushplus_url` 覆盖、以及 `ChannelService.Create/Update` **不调用 `ValidateConfig`** 在 v2.0.0 **均已成立**（合成人已复核 v2.0.0 的 `channel_service.go` 全文无 `ValidateConfig`）。→ 既有问题。
- **问题机制**：渠道 `Create`/`Update` 完全不执行 `ValidateConfig`（只有 `Test` 与 `Send` 路径会），因此 `webhook_url`/`pushplus_url` 可写入**任意字符串**，包括 `http://169.254.169.254/latest/meta-data/`、`http://10.0.0.5:6379/`、`file:///etc/passwd`。之后任一绑定该渠道的任务发送时，`postJSON`/`PostForm` 直接请求该地址；响应体被读入（`io.LimitReader(..., 64*1024)`）并**写进 `task_logs.response`/错误信息**（`notification_service.go:160-173` 落库 `err.Error()`）→ 有日志读权限的用户（所有登录用户均可 `GET /api/logs`）即可读取该响应 → 云主机元数据/内网服务响应外带。
- **影响**：需管理员权限才能配置渠道，故非「未授权 SSRF」；但管理员配置「webhook 地址」时通常不会意识到自己在给服务端开一个任意 URL 请求器，且**响应内容会落进所有登录用户可读的日志**，形成「管理员配置 → 普通用户外带」的权限跨越。`file://` 在 Go 的 `http.Client` 下会报 `unsupported protocol scheme`（不构成本地文件读取），但错误信息里会带上路径。
- **修复建议**：`ChannelService.Create/Update` 调用 `ValidateConfig`；在 `postJSON`/`sendPushPlus` 前做 URL 校验（仅允许 `https` 或显式白名单域名，拒绝环回/私有/链路本地地址）；`task_logs.response` 对非 2xx 响应体做截断或脱敏。
